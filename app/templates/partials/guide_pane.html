How work moves through Forge

  1. Assign. Select issues in Issues. Forge runs a local Droid session in an isolated workspace clone.
  2. Agent turn. Each turn is a separate attempt with its own usage. A completed turn only means the agent stopped; it may leave a local candidate commit. You can send a follow-up (a new attempt) or stop an active turn. Restarts never resume work on their own.
  3. Acceptance checks. On a task's detail page, run the configured checks. The app runs them in a clean checkout of the exact candidate commit, without GitHub or operator credentials.
  4. Restricted review. Start a review of the same commit. The reviewer can only read, grep and glob the exact diff. It runs no commands or tests.
  5. Your approval. When checks passed and the review approved that exact commit, you can approve it. Approval covers only that commit, is not a GitHub review, and grants no merge permission. A new commit needs fresh checks, review and approval.
  6. Publication. A separate, explicit step pushes the approved commit to the allowed branch (never by force) and creates or reuses a draft pull request. It is refused when policy does not permit GitHub writes.
  7. Remote CI. GitHub CI can only run after publication. Forge observes it read-only and shows pending, failing, passing or unavailable states as they are.
  8. Merge. Forge never merges or enables auto-merge. Merging stays a human decision on GitHub.

Reviewing existing pull requests. Use PR reviews to assign an open pull request, including a draft, to a restricted review. The review detail shows the reviewed head commit, the AI verdict and findings, and separately what was recorded on GitHub.

A self-review that GitHub refuses as a formal approval is posted as a comment and labeled as such; it is not a formal GitHub approval.
